# SLO workload

## GitHub-hosted Bridge recovery qualification

`.github/workflows/slo-2dc.yml` runs native Query on `ubuntu-24.04` with a
pinned SLO Action, a resolved server image and a bounded four-node topology.
The 15-minute functional profile uses 50 reads/s and 10 writes/s. It does not
replace the larger runner's performance baseline or activate its `SLO` label.

Transient operation errors are diagnostic: the required behavior is continued
work and intact acknowledged data. One additional Go Query driver stays alive
through all five upstream Bridge scenarios, performs serializable write/read
transactions with a 30-second operation context, and audits all acknowledged
rows after chaos completes. The workload image includes this probe only when
built with `BRIDGE_PROBE=true`; normal SLO images keep their existing entrypoint.

The gate requires:

- completion of all five scenarios without restarting the chaos process;
- successful control transactions while each database-node outage is in effect,
  after each recovery, and at the end of the run;
- recent successful native reads and writes;
- every acknowledged control row present with the expected payload;
- no OOM or unexpected automatic YDB-node restart.

Docker stop/start events define the actual unavailable-pile intervals. Short
restarts used during rejoin are excluded from the outage-window count. The
native error count and failed probe calls remain in the evidence but do not
fail a recovered client by themselves. A client that only resumes when the
old pile comes back fails the unavailable-pile check.

Compose 2.40.3 is installed explicitly for the Action's `up --quiet-build`.
The hosted adapter supplies the server build argument, bounds node memory,
aligns workload reservations with its limit and disables `extra-nodes`.
The server binary and Action lifecycle sources are unchanged.

`go-hosted-2dc` artifacts contain the combined `result.json`, native/probe/chaos
logs, stop/start events and the resolved server image. Recovery/data oracle
tests run before deployment. After the workflow is available for dispatch:

```bash
gh workflow run slo-2dc.yml --ref <branch> -f server_image=<image-reference>
```

This qualifies an already configured Bridge cluster. Config v1/v2 conversion
and per-database storage migration are separate scenarios.

SLO is the type of test where app based on ydb-sdk is tested against falling YDB cluster nodes, tablets, network
(that is possible situations for distributed DBs with hundreds of nodes)

### Implementations:

- `native`       - over `./native` driver
- `database/sql` - over `./database/sql` driver
- `gorm` - over `gorm` driver
- `xorm` - over `xorm` driver

### Usage:

The workload runs in a single mode: creates table, fills with initial data, runs read/write workers, then drops table.

All configuration is done via environment variables.

### Run example:

```bash
export YDB_ENDPOINT=grpc://ydb:2136
export YDB_DATABASE=/Root/testdb
export WORKLOAD_DURATION=600
export OTEL_EXPORTER_OTLP_ENDPOINT=http://ydb-prometheus:9090/api/v1/otlp
export PROMETHEUS_URL=http://ydb-prometheus:9090

./slo-native-table
```

### Environment Variables:

**Required:**
- `YDB_ENDPOINT` - YDB endpoint to connect to
- `YDB_DATABASE` - YDB database to connect to

**Optional:**
- `WORKLOAD_REF` - workload ref label (e.g., `current`, `baseline` for A/B comparison)
- `WORKLOAD_NAME` - workload name (used as label in metrics and table path prefix)
- `WORKLOAD_DURATION` - run time in seconds (default: 600)
- `WORKLOAD_SHUTDOWN_TIME` - graceful shutdown time in seconds (default: 30)

- `WORKLOAD_BATCH_SIZE` - batch size for bulk operations (default: 1)
- `WORKLOAD_PARTITION_SIZE` - partition size in MB (default: 1)
- `WORKLOAD_INITIAL_DATA_COUNT` - initial rows count (default: 1000)
- `WORKLOAD_MIN_PARTITIONS_COUNT` - minimum partitions (default: 6)
- `WORKLOAD_MAX_PARTITIONS_COUNT` - maximum partitions (default: 1000)

- `WORKLOAD_READ_RPS` - read RPS (default: 1000)
- `WORKLOAD_WRITE_RPS` - write RPS (default: 100)
- `WORKLOAD_READ_TIMEOUT` - read timeout in ms (default: 10000)
- `WORKLOAD_WRITE_TIMEOUT` - write timeout in ms (default: 10000)

- `OTEL_EXPORTER_OTLP_ENDPOINT` - OTLP endpoint for metrics
- `PROMETHEUS_URL` - Prometheus endpoint

## Authentication

Workload uses anonymous credentials.

## What's inside
When running, the program creates three jobs: `readJob`, `writeJob`, `metricsJob`.

- `readJob`    reads rows from the table one by one with random identifiers generated by writeJob
- `writeJob`   generates and inserts rows
- `metricsJob` periodically sends metrics to Prometheus

Table have these fields:
- `id Uint64`
- `hash Uint64 Digest::NumericHash(id)`
- `payload_str UTF8`
- `payload_double Double`
- `payload_timestamp Timestamp`
- `payload_hash Uint64`

Primary key: `("hash", "id")`

## Collected metrics
- `oks`      - amount of OK requests
- `not_oks`  - amount of not OK requests
- `inflight` - amount of requests in flight
- `latency`  - summary of latencies in ms
- `attempts` - summary of amount for request

> You must reset metrics to keep them `0` in prometheus and grafana before beginning and after ending of jobs

In `go` it looks like that:
```go
func (m *Metrics) Reset() error {
    m.oks.WithLabelValues(JobRead).Set(0)
    m.oks.WithLabelValues(JobWrite).Set(0)

    m.notOks.WithLabelValues(JobRead).Set(0)
    m.notOks.WithLabelValues(JobWrite).Set(0)

    m.inflight.WithLabelValues(JobRead).Set(0)
    m.inflight.WithLabelValues(JobWrite).Set(0)

    m.latencies.Reset()

    m.attempts.Reset()

    return m.Push()
}
```
